# Percí v1.7.2 | Integración QA de sincronización atómica

**ESTADO: no publicado.** Versión de producción vigente: **v1.6.4**. Requiere QA real antes de cualquier cutover.

## Contrato
- `GET /api/cloud/data` devuelve el snapshot habitual más `revision` en modo QA. Se lee la revisión **antes y después** de las siete lecturas; se reintenta si cambió.
- `POST /api/cloud/sync` en modo QA requiere `{atomic:true,snapshot,expected:{revision:N,...},deletions:{routines:[],records:[],habits:[]}}`. El servidor usa exclusivamente el usuario autenticado por cookies HttpOnly para derivar el JWT y llamar con ese JWT a `/rest/v1/rpc/perci_commit_snapshot`.
- Respuesta correcta `{revision:N+1,...}`. Si hubo otra escritura, PostgreSQL devuelve HTTP 409. La UI vuelve a leer y hace reconcile de tres vías; NO descarta el outbox.
- Los borrados se incluyen en **esa misma** operación atómica. `POST /api/cloud/delete` se rechaza (409) mientras esté activo el modo QA. El servidor legacy de producción sigue en modo anterior.
- La PWA confirma un GET posterior con la **misma nueva revisión** y contenido esperado antes de eliminar la cola local y los tombstones.

## Qué cambia
- `server/perci_atomic.py`: guardas de QA + revisión coherente + validación + llamada a RPC.
- `api/shared.py`: conexión controlada de API a motor, sin rutas nuevas ni secretos.
- `public/src/account.js`, `public/src/app.js`: un único POST para upserts y deletions; revisión confirmada antes de limpiar cola.
- `public/index.html`, `public/sw.js` y grafo de JS: v1.7.2 (una única identidad de módulos).
- SQL adicional **solo en perci-qa**: revoca escrituras REST directas a tablas para que clientes antiguos no salteen el CAS, manteniendo RLS SELECT y RPC SECURITY DEFINER.

## Guards de entorno
Antes de habilitar QA en una instancia **Preview o local**, definir:

- `SUPABASE_URL=https://<project-ref-QA>.supabase.co` (solo QA)
- `SUPABASE_PUBLISHABLE_KEY=sb_publishable_...` (clave pública QA)
- `PERCI_ATOMIC_QA_ENABLED=YES_QA_ONLY`
- `PERCI_ATOMIC_QA_PROJECT_REF=<project-ref-QA>`

Si el host de la URL no coincide con el ref QA o `VERCEL_ENV=production`, se rechazan las operaciones. **Nunca configurar el flag en el Vercel público.** No insertar service_role ni ninguna clave secreta.

## Riesgos / límites documentados
- El GET de múltiples tablas es coherente por revisión doble, pero puede tener reintentos ante escrituras continuas; la transacción real se garantiza en cada RPC, no en el GET de varios endpoints.
- Un POST pudo haber confirmado en la BD aunque el navegador perdiera la respuesta. Se conserva el outbox; el siguiente GET + merge identifica la versión nueva (no hay rollback del commit confirmado).
- Revocar direct DML no invalida JWTs existentes ni reemplaza pruebas de aislamiento de INSERT/DELETE cruzados: verificar con usuarios QA reales.
- La limpieza de las 6 pruebas QA anterior no garantiza que `perci_profiles` y `perci_sync_state` queden sin filas: se dejan deliberadamente para verificar revisiones posteriores.
- La función SQL v1.7.1 fue validada con 6 PASS reportados por el script de QA, pero la integración web **todavía no** se ha probado en dispositivos.
